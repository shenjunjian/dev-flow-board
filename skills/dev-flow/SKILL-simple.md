# 工单流

工单就是 GitHub issue，它有“需求、开发、检视、合入”四个阶段，用状态 label 跟踪阶段，简单任务可以没有检视阶段，检视到错误后必须回到开发阶段。

## 前提

- 默认 `gh` 已安装并登录。不要预先检测。命令因未安装或未登录失败时，再让用户安装 GitHub CLI（https://cli.github.com）并执行 `gh auth login`。
- 在仓库目录中执行。`gh` 使用当前目录对应的 GitHub 仓库。

## 标签管理

状态 label，同一时刻只保留一个，且按该顺序流转：`Story`、`WaitDev`、`Dev`、`DevDone`、`Review`、`ReviewDone`、`ReviewErrors`、 `Merged`。

重要性 label：`High`、`Low`。用户未说明时用 `Low`。更换状态时不添加、不移除重要性 label。

任务类型 label: `feature` / `bug` / `refactor`。对应创建代码分支或pr提交的标题时， `bug` 类型要用 `fix` 前缀代替。

## 编号

- 发布不需要编号。
- issue 与 PR 的编号相互独立，`#N` 通常是工单编号，在合入时可能是 PR 编号。 通常工单信息和 PR 信息可以互相查到对方的，先用对应的 `view` 确认存在；确认失败就停止并说明原因。

## 用户触发指令

用工单标签管理着项目的开发，如果用户发出的指令，但工单不满足入口标签时，说明原因并停止。此时不改 label，不关闭工单。

### 发布

用户说发布需求、任务或工单。

从对话归纳标题、正文、重要性（未说明则 `Low`）和任务类型。创建工单，贴上 `Story`标签 和重要性 label 和 任务类型 label。
尽量保持用需求的原始表达，不发散思维，不猜测需求，因为真正的需求详情是在`分析、拆解`的步骤中细化。

本阶段不阅读源码，不改代码，不提交。

### 分析 / 拆解

用户说分析或拆解，且已确定工单编号，入口标签 `Story` 。

读取工单和仓库代码，然后使用 `grilling模式` 澄清需求，对齐开发目标，之后根据需求的复杂度，分以下2种情况，将内容在写**一条**评论：

- 简单任务，适合一次性开发：在issue中写`Spec文档` ，贴 `WaitDev` 。
- 用户要求开发计划，或任务适合分步：在issue中写`Spec文档` ，贴 `WaitDev`。 然后生成一份`todos`列表，并询问用户这些问题：`粒度合适吗？（太粗 / 太细 / 应该生成多少个todos），阻塞关系对吗？ `。确认答案后，将`todos`列表追加到`Spec文档`下面。之后为每个 todo 建一个子工单，贴 `WaitDev` 和重要性 label和任务类型label。有阻塞关系时，添加 `blocked_by` 表示。子工单各自走后续状态机。

一个 `todos` 任务是一次性改动功能每一层（schema、API、UI、测试），它聚焦一个功能点且落地之后单独就能演示和验收。每一个todo任务应该在一个全新的上下文窗口里装得下。

本阶段不动源码，将所有结果写入工单的评论中。如果引入新的`术语` 或 `架构决策记录`，记录在评论中，在实现、开发功能时写入 `AGENTS.md`中。

### 实现 / 修复 / 开发

用户说实现、解决或修复，且已确定工单编号，入口标签`WaitDev` 或 `ReviewErrors` 。

如果当前工单是一个单独issue的时候，先读取正文和评论中的方案，贴 `Dev`，之后再进行开发。当前任务/工单引入新的`术语` 或 `架构决策记录`，请务必记录在 `AGENTS.md`中,工单中的`Spec文档`部分要保存到源码的 `.specs`中去。

如果当前工单是父工单，它具有`todos`列表时候，停下来，并告诉用户应该先开发哪个子工单。

本阶段不 commit、不建 PR、不关闭工单。

### 提交 / 开发完成

用户说提交代码或开发完成，且已确定工单编号，入口标签 `Dev`

工作区中，若用户未commit，则提交标题为`fix(..): ...`的模式，使用任务类型 feat/fix/refactor 做前缀。提交说明不包含 `Fixes`、`Closes`、`Resolves` 加 `Closes #编号`。

若该工单已有开放 PR 则沿用。否则先把当前分支推送到远端，再创建 PR：base 为仓库默认分支，head 为当前分支，正文包含 `Closes #<工单编号>`， 请参考`pr 内容格式`的说明。PR 就绪后，把状态换成 `DevDone`。

本阶段不动源码，也不自动合入Pr。

### 检视 / 审核

用户说检视或审核，且已确定工单编号，入口标签 `DevDone`

先贴 `Review`，再查看该工单关联 PR 的详情和修改内容，依据`检视方法说明`进行检视。

- 有问题：每个问题一条评论，然后换成 `ReviewErrors`。
- 无问题：换成 `ReviewDone`。

本阶段不关闭工单，不删除 `blocked_by`。

### 合入

用户说合入PR时，且已确定工单编号，入口标签`ReviewDone` 或 `DevDone`

从工单的关联信息中读取pr 号，读取 PR 的 `closingIssuesReferences` 和 `mergeable`。`mergeable` 不是 `MERGEABLE` 时停止并说明原因。

执行 `gh pr merge <n> --squash`。如果用户没有 pr merge的权限，提醒用户未能合入就停止。合入成功后贴`Merged`，合并失败时不关闭工单，不卸下 `ReviewDone`。

如果目前关联工单是一个子工单，则将其父工单的 `todos`中的当前项的`status`修改为`completed`，如果父工单的所有 `todos`都已完成，就将父工单的状态标签修改为 `Merged`， 父工单也全部结束，完成使命。

## Spec文档编写说明

Spec文档将之前的对话变成一份规格说明，它固定下来的那些决定，并结合AGENTS.md记录术语和架构决策记录来生成Spec文档的内容。在`分析拆解`需求时，它保存到工单评论上，在`开发`时，要保存到项目的 `.specs` 目录中。

`.specs/index.md` 保存所有spec文档的索引，如果没有则创建它。每次编写Spec文档时，先读取索引判断是否已有对应的Spec, 如果存在同主题的Spec，则将它们写在一起，并在最后追加 `变更历史`，记录变更的描述以及变更时间。如果不存在同主题的Spec，则新建它。

## todos 格式

示例：

```md
todos:

- id: <任务标题>
  content: <一句话说明>
  status: <pending|completed>
```

## grilling 模式

每一轮按下面的格式组织：

```
❓ **Q1** - **<问题标题>**: <问题内容，可以有多句话>

➡️ <你推荐的方案>
➡️ <候选的方案1>
➡️ <候选的方案2>
➡️ <用户输入自己的决定>

```

所有的问题要统一编号，后一轮对话的编号要大于上一轮次。

其它参考matt pocock's grill-me skill
